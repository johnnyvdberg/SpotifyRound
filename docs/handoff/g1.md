# G1: what the GL backend gives us that we build by hand

Result: **nothing to land.** The one prototype worth measuring (compressed textures) moved the
frame by 0.00 ms; the other candidates are either already what the GPU does best or cannot pay.
Measured 2026-11-01 on the Pi 5, OpenGL ES (Mesa 26.2.2), branch `tooling`.

## What the adapter exposes

`spotify-round-tests gpu_cost::adapter_report --ignored --nocapture` (new; add `WGPU_BACKEND=gl` or
`vulkan`) prints the backend, features, downlevel flags, limits and the usage/filter flags of the
formats the dive uses. On the Pi:

| | GL (wgpu GLES, default) | Vulkan (v3dv) |
|---|---|---|
| Driver | OpenGL ES 3.1 Mesa 26.2.2 | V3DV Mesa 26.2.2 |
| Texture compression | **ETC2/EAC and ASTC LDR** (+ASTC sliced 3D) | ETC2/EAC, ASTC, BC |
| `Rgba32Float` | **filterable** (`FLOAT32_FILTERABLE`) | not filterable |
| `Rgba16Float`, `Rg11b10Ufloat`, `Rgb10a2Unorm` | filterable, blendable | same |
| Texture size / array layers | 4096 / 2048 | same |
| Sampled textures, samplers per stage | 16 / 16 | same |
| Timestamp queries | none | inside encoders and passes |
| Downlevel flags GL lacks | `BASE_VERTEX`, `READ_ONLY_DEPTH_STENCIL`, `MULTISAMPLED_SHADING`, `DEPTH_BIAS_CLAMP`, `FULL_DRAW_INDEX_UINT32`, `VIEW_FORMATS` | |

Nothing the dive needs is missing on GL (it renders there already); features that exist only on
GL (`FLOAT32_FILTERABLE`, `DUAL_SOURCE_BLENDING`) must not be depended on, since Vulkan stays the
fallback and the shaderdb path.

## Inventory: what the dive builds by hand, and the verdict

| Hand-built | Alternative | Verdict |
|---|---|---|
| 19 surface layers of 256x256 RGBA8 with a CPU mip chain (`textures::paint_all`), one `texture_2d_array` | ETC2/ASTC blocks; hardware mip generation | **Compression: measured, no gain (below).** Hardware mip generation does not exist in wgpu (it would be a blit shader), and the CPU chain is better: it filters the packed relief channels in float, once at start-up. |
| Level of detail worked out in the shader (`tap`, `textureSampleLevel`) | gradient sampling | Already chosen deliberately: the V3D has no sampling by gradients (scene.wesl comment). |
| Anisotropic filtering | sampler `anisotropy_clamp` | Already measured and dropped (0.50 ms, no visible change; comment in `Nautilus::build`). |
| Surfaces as an array, sky as a cube array | texture arrays vs atlases | Already arrays. |
| Seabed relief `Rgba32Float`, four `textureLoad`s and a hand bilinear in `relief()` | one hardware-filtered fetch from `Rgba16Float` (filterable on both backends) | **Dead code.** `relief()` is called only by `ground_parts()`, called only by `ground()`, which nothing calls: the terrain is built on the CPU (`terrain.rs`). The 4 MB texture (512x512x16 B) is uploaded for every visit and bound, but never sampled. Deleting `relief`, `ground`, `ground_parts` from `scene.wesl` and the texture from `Nautilus::build` saves memory and a 4 MB write per visit, no frame time. Not done here: it edits `scene.wesl`, which the performance agents own. |
| Caustic shimmer, 256x256 R8 | - | One fetch already. |
| `textureGather` | 4 texels in one fetch | No bilinear lookup is hand-built any more (the relief one is dead), nothing else gathers. |
| Instancing (`first_instance` for the tunnel and fading draws) | native base-instance draws | GLES 3.1 has no base-instance; wgpu's GL backend moves the instance buffer offset instead. That costs CPU per draw, and `perf-bottlenecks.md` 3.9 finds the CPU is not a limiter. Not measured further. |

## The prototype: ETC2 for the surfaces

The TMU is busy, so smaller texture reads were the most promising idea. A prototype (not kept; it
was a local patch to `gpu::open` requesting `TEXTURE_COMPRESSION_ETC2` and to `Nautilus::build`,
behind `DIVE3D_PROTO_ETC2`) created the `surfaces` array as `Etc2Rgba8Unorm` (8 bits a texel, a
quarter of RGBA8's size) with every block zero. That costs the same fetches as real ETC2 data would
and reads one quarter of the bytes, so it is an upper bound on what compression can win without
writing an encoder. (A zero-block texture draws wrong, as the shots confirmed: 40-46% of pixels
moved in coral; the path really was in use.)

Full default `hotspots` (4 visits, 168 places), same binary, kiosk frozen:

| run | median | worst | places over 11 ms |
|---|---|---|---|
| base | 8.27 ms | 10.89 | 0 |
| base again (noise floor) | 8.29 | 10.87 | 0 |
| ETC2 surfaces | 8.30 | 10.86 | 0 |

Per-sea medians agree to 0.02 ms except atlantis (-0.12), coral (-0.13), brine (-0.11) and bloom
(+0.15), the seas with few surface fetches, which is run-to-run scatter rather than an effect.
So the surface fetches are limited by the TMU's instruction slots and latency, not by bytes, and
quartering the bytes does nothing. ETC2 would also cost visuals: the layers pack relief in their
green and blue channels, which block compression smears. **Ruled out**; do not retry unless a
shader starts to fetch much more per pixel.

ASTC would be the better fit for packed data but cannot beat a zero-byte-cost bound, so it was not
tried.

## Tooling this task used

`deploy/shots.sh pi NAME` (I1) rendered the coral places on the Pi through the test binary with and
without the prototype; `bench-pi.sh run` carried the hotspot numbers. `effect_cost` on the Pi runs
for more than 35 minutes (it freezes the kiosk the whole time) and was stopped; prefer
`bench-pi.sh features` (4 minutes) for pricing.
